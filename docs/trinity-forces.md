# Trinity:Context、Intent、Forces

狀態:訪談進行中(2026-11-14 開始)。這份文件是工作底稿,隨訪談更新。
方法:pattern language。順序是 Forces → Problem → Solution。使用者主導,最終版本以使用者的話為準。

來源欄的意思:
- **你**:使用者說過的話。
- **證據**:開發過程中實際發生的事。
- **假設**:Claude 的推測,使用者還沒確認。

## 1. Context

- 使用者一個人同時指揮多個 AI agent session,主要在 Claude desktop 和 Claude Code。
- 已有的資產:
  - GTD Island:macOS 瀏海面板加 Option+Space 搜尋框(本 repo)。
  - Notion GTD:Projects、Next Actions、Handoff 流程。
  - Trinity 舊專案:`trinity handoff` CLI(Go)和記憶庫 PoC(Python、PostgreSQL、MCP)。
  - `agent-config` repo:規則和 skill,同時連到 Claude 和 Codex。
- 現況:Claude 的 agent 領先,使用者沒有實際需要換廠商。

## 2. Intent(使用者的話)

- 「打造一個以我為中心我們自己開發的工作環境」。
- 「我自己的工作的交接我需要有一個中控平台那我可以自由的交接…與管理自己的工作流與任務」。
- 「重點是人類要怎麼掌握全局? 東西太多了 就像黃仁勳 底下有 60 個直屬下屬」。
- 名稱:Trinity。GTD 和記憶庫是可插拔的部分。Trinity 要追蹤使用者啟動的所有 agent。

## 8. Problem

還沒寫。等第 7 節的 1 到 3 回答後,由使用者先寫。句型:

> 當我 ___ 的時候,我沒辦法 ___,因為 ___。

### P1 回報要多精準(使用者提出,2026-11-14;措辭待確認)

使用者的觀察:「context 太少會誤判,太多有代價」不只對 agent 成立,對人也成立。所以 context 有兩個方向,是同一種拉扯:

| 方向 | 太少 | 太多 |
|---|---|---|
| 人 → agent(派工時) | agent 誤判(B1) | 有代價(B3) |
| agent → 人(回報時) | 人誤判,或不敢相信而親自去看(A1 ↔ B1、B2) | 佔用注意力(A1) |

草稿:

> 我靠 agent 的回報掌握進度。回報太簡略,我會誤判,或不敢相信而親自打開 session。回報太詳細,又佔用我有限的注意力。
> 判斷標準:讀完一份回報,我能直接做出它需要我做的決定,不用打開 session;而且讀它的時間短到我願意每一份都讀。

### P2 利用各家功能,又要能快速遷移(使用者提出,2026-11-14;措辭待確認)

來自 C1 ↔ C2、C4 和 C1 ↔ C3、D1。使用者的話:「該要如何利用某些各家的 feature 但是又能保持快速遷移」。

草稿:

> 我想盡量利用每個品牌自己的功能,不重做它們。但我用得越深,工作方式就越長在那個品牌上,要換的時候越搬不動。而遷移的能力平常用不到,不用就會壞。
範圍(使用者確認,2026-11-14):「遷移」只指兩樣,進行中的一件工作,以及入口和習慣。規則、skill、任務狀態已經搬得動。自動化機制留給各家,不在範圍內。

> 判斷標準(候選,待使用者挑選):
> - 一件進行中的工作,能在 N 分鐘內交給另一個品牌的 agent 接手,不用我重新解釋。
> - 某個品牌改了內部格式時,要修的地方只有一處。
> - 遷移的路徑有被定期實際走過,不是只在需要時才第一次用。

### P3 跨廠商的 traceability(使用者提出,2026-11-14;措辭待確認)

traceability(可追溯性):事後能查出一件工作由誰做了什麼、依據哪個決定、證據在哪。

來自 B1、B2、A6 ↔ C4、B3、A1。

> 我的工作分散在多個品牌的 agent 上。我想事後查得出每件工作的經過。但每個品牌把紀錄放在自己的地方、用自己的格式,而完整的紀錄又多到沒有人讀得完。
> 判斷標準:對任何一件工作,我能在一個地方回答「誰做了什麼、依據哪個決定、證據在哪」,不論它是哪個品牌的 agent 做的。

使用者同時提了一個解法:「centralized 的 message platform」。它屬於 Solution,已記在第 9 節。

### 其餘的 Problem(Claude 依第 4 節的拉扯起草,2026-11-14;全部未確認)

**P4 被打斷,還是漏掉**(A3)

> 有 agent 在等我時,我想盡快知道,不讓它空等。但每次通知都會打斷我正在做的事。
> 使用者的回答(2026-11-14):「不用打斷吧? 跳出來 就像通知一樣 我可以選擇隱藏 代表等一下在處理 也可以立刻處理」。
> 判斷標準:有 agent 在等我時,入口像通知一樣顯示出來,但不搶走鍵盤焦點,也不擋住我正在做的事。我可以隱藏它(代表等一下處理),也可以立刻處理。被隱藏的項目之後仍然找得到。

**P5 想看到流程階段,但流程不固定**(A4 ↔ E6)

> 我想看到每件工作走到哪一步,才能只修出錯的那一步。但我的工作很多步驟是人的判斷,每件工作的流程不一樣,畫不成一張固定的圖。
> 判斷標準:對任何一件進行中的工作,我能說出它現在在哪一步、下一步是什麼、卡在誰。

**P6 排序要自己決定,但東西太多排不動**(A5 ↔ A8)

> 做哪件事由我決定,我不要工具替我排。但待辦太多又沒分類時,我自己也排不出來,最後不知道從哪開始。
> 判斷標準:打開入口後,我能在一分鐘內選出現在要做的那一件,而且那是我自己的選擇。

**P7 在入口回應 agent,但不能搶走或代替原本的互動**(D2 ↔ B5)

> 我想在入口直接回應 agent,不用跳到它的 app。但入口攔截互動會讓我在原本的 app 反而答不了,而且在看不到完整脈絡的地方按「允許」有風險。
> 判斷標準:入口上的任何回應,在原本的 app 裡仍然可以照常做;入口只在資訊足夠判斷時才提供回應按鈕。

**P8 同時做很多事,但每次接手都要重新載入脈絡**(A6、A2、D7 ↔ A1)

> 我同時推進很多件工作,所以經常要從一件切到另一件。但每次接手都要找到對應的 session、想起做到哪、在等什麼,這很累。
> 判斷標準:從決定接手一件工作,到我能開始下一個動作,時間在 N 秒內,而且不用讀對話紀錄。

**P9 可插拔和跨平台,但我能對齊和驗證的範圍有限**(E3、E4 ↔ D3、E1、A1、A5)

使用者的修正(2026-11-14):「是一個人沒錯 但是 只要對齊方向 可以由 agent 加速」。所以限制不是寫程式的人力,而是使用者對齊方向和驗證結果的注意力。

> 我希望各功能可以獨立替換,也希望跨平台。寫程式可以交給 agent,所以人力不是限制。但每多一個模組或平台,就多一樣我要對齊方向、確認真的能用的東西,而我的注意力有限。
> 判斷標準:待定。要先決定跨平台是現在的需求,還是將來的保險。

**P10 不同品牌的 agent 之間沒有共享的目前狀態**(使用者提出,2026-11-14;措辭待確認)(B1、C1 ↔ B3、P9)

使用者的話:「我們自己的 memory space 也是很重要的因為它可以讓不同家的 agent share 目前的狀態但這個可大可小」。

> 我的工作分散在不同品牌的 agent 上,每個 agent 只知道自己 session 裡的事。我想讓它們都能讀到目前的狀態。但這件事可大可小:放得太少沒有用,放得太多又回到 context 過多,而且要維護的範圍變大。
> 判斷標準:一個新開的 agent,不論品牌,不用我解釋就知道這件工作目前的狀態和已做的決定。

「我們自己的 memory space」是解法,已記在第 9 節。

### 順序與原則(使用者同意,2026-11-14)

使用者的優先:最主要是「能夠快速的跳到對的地方而不用從很多 session 之間搜尋」。P5 不急。P1、P4、P6、P8、P9 都重要。

原則:

1. 每天會用到的先做。每天用就等於每天驗證。
2. 每一步使用者能在幾分鐘內親手驗證。不能驗證的步驟不算完成。
3. 從已經有的東西往前長,每一步只加一小塊。
4. 產生資料的先於使用資料的。
5. 結構性的限制(P2、P9)不排進順序,當作每一步的規則:狀態放自己的資料裡,品牌只是接入點,核心不綁 macOS。

順序:

| 順序 | Problem | 最小的一步 | 使用者怎麼驗證 | 狀態 |
|---|---|---|---|---|
| 1 | P8 接手成本 | 搜尋框。補上:每一列顯示「在等什麼」;終端機的 session 也能跳 | 按 Option+Space,十秒內到達對的 session | 桌面 session 的跳轉已由使用者驗證(11-14)。終端機 session 跳不過去,待做 |
| 2 | P6 排序 | 不打字時列出使用者自己寫的 Next Action,依 Project 分組,Enter 跳到負責的 session | 打開後一分鐘內選出現在要做的那件 | 未開始 |
| 3 | P4 打斷或漏掉 | 依使用者的答案設定瀏海什麼時候亮 | 用一天,數被打斷幾次、漏掉幾次 | 等使用者回答 |
| 4 | P1 回報 | 每個工作步驟結束時,agent 寫固定格式的短回報,入口直接顯示 | 讀完能做決定,不用打開 session | 未開始 |
| 5 | P3 traceability | 把前四步累積的事件整理成可查的紀錄 | 挑一件上週的工作,在一個地方查出經過 | 未開始 |
| 6 | P7 在入口回應 | 資訊足夠時才提供回應按鈕 | 同一個請求,在入口和原本的 app 都答得了 | 未開始 |
| 7 | P2 遷移 | 接上第二個品牌(Codex),實際交接一件工作 | 一件進行中的工作交過去,不用重新解釋 | 未開始 |
| 8 | P5 流程階段 | 使用者說不急 | — | 延後 |

- P0 不在表裡。它是衡量標準:每做完一步,量一次「不打開任何 session,一分鐘內能不能說出全局」。
- P10(共享的目前狀態)還沒排進順序。Claude 的建議:它跟著每一步長大,最小的版本在第 4 步出現(入口已有的狀態和回報,讓 agent 也讀得到),第 7 步時必須足夠讓另一個品牌接手。待使用者確認。

## 9. Solution(暫放,Problem 確定後才討論)

- 使用者提的:中控平台,即自己的入口。
- 使用者提的(針對 P10):我們自己的 memory space,讓不同品牌的 agent 共享目前的狀態。範圍可大可小。既有的記憶庫 PoC 是候選的基礎。
- 使用者提的(針對 P3):centralized 的 message platform,即所有品牌的 agent 都把訊息送到同一個地方。
- Claude 提的資料流草稿:https://claude.ai/artifact/7sq5Ea6hcHaK5XdvCKSkYm 。訪談後要重畫。
- 記憶庫的角色:若 B1 是主因,記憶庫和交接負責在 agent 開工前送上相關的 context,同時受 B3 限制。
- 尚未回答:由誰決定哪些 context 和一件工作相關,是 agent 自己查,還是入口在派工時先挑好。
